## Role in this project

The post-quantum, hybrid-indexed, verifiable baseline — and the only baseline
whose verification is already **per record** rather than aggregated. That makes
it the comparison point for verification *cost* in Experiment 4 while being
deliberately absent from Exp. 4's `granularity` arm, whose all-or-nothing
question does not
describe it. Its absence from that panel is a statement about the scheme, not a
gap in the data.

Unlike Scheme 41, its post-quantum claim is real: the construction is
lattice-based throughout, with ML-KEM-768 and ML-DSA-65, and the manuscript's
comparison table credits it accordingly.

## How the scheme works

```
src/scheme.py        Phases 1–5
src/abe.py           lattice CP-ABE — off the measured path
src/hybrid_index.py  the fog-side hybrid index; what Exp. 2 searches
```

Five phases, single **Trusted Authority** — the paper never claims
multi-authority, and this repository deliberately does not describe it as such:

| Phase | What happens |
|---|---|
| 1. System setup | ABE setup, Kyber (ML-KEM-768), Dilithium (ML-DSA-65) |
| 2. Edge-side encryption | Algorithm 1, `EdgeEncrypt` |
| 3. Fog verification + indexing | hybrid index construction, Merkle partition roots |
| 4. Search | Algorithm 2, `SearchExec` |
| 5. Retrieval + verification | Algorithm 3, `RetrieveVerify` |

**The hybrid combiner is the headline security property.** Phase 2 encapsulates
the record key **twice** — under the lattice CP-ABE and under ML-KEM-768 — and
combines them with HKDF:

```
K_hyb = HKDF(K_abe || K_kem)
```

which stays secure if *either* primitive does. It is implemented as the paper
states rather than collapsed to a single encapsulation; collapsing it would
remove the scheme's headline property while making it look faster.

**The hybrid index** (Phase 3) tokenizes each record's searchable fields with a
PRF and files the tokens into five structures, each chosen for one query shape:

| Structure | Serves |
|---|---|
| B+-tree | exact keyword lookup |
| bucketed bitmap | numeric range predicates |
| equality bitmap | categorical predicates |
| epoch partitions | temporal predicates |
| n-gram map | fuzzy match, scored against a threshold |

Search intersects candidate sets across whichever structures the query touches.
**That intersection — not any lattice operation — is the whole of Experiment 2's
measured path**, which is precisely the paper's claim: the client only generates
PRF tokens and the fog does the index work.

Two choices that make the baseline harder rather than easier:

- **The B+-tree is a real B+-tree.** A dict would serve exact lookup faster and
  would flatter this baseline, but the paper specifies a B+-tree, costs it at
  `O(log n)` in Table II, and reports its fanout behaviour. Lookups really do
  descend it.
- **Tokens are keyed, not hashed.** `token(w) = PRF_k(w)` under the fog's
  tokenization key, per Phase 3. An unkeyed hash would leak the keyword to
  anyone holding the index and make the trapdoor derivable without the key.

## Trapdoor generation binds to the attribute key

`TokenTrapdoorGen(SK_A, T, range, op, epoch)` — Ref[54] L798. Three requirements,
all of which the implementation missed until 2026-09-12:

| Paper | Line | What it requires |
|---|---|---|
| §IV-C.5b | L563-565 | the trapdoor is built by "binding query tokens to the user's attribute-based secret key" |
| §IV-C.5b | L566 | `σ_user = Dilithium3.Sign(sk_U, H_2(TD))` — the **user's** key |
| IND-CKA game | L798 | `SK_A` is the first input to `TokenTrapdoorGen` |
| Theorem 2 | L816 | the proof rests on tokens "further bound to the user's attribute key `SK_AU`" |

**What was wrong.** `trapdoor()` hashed the PRF tokens alone and signed with
`keys.edge_signing_key`. So there was no attribute-key binding at all — the
precondition of the scheme's own security proof did not hold — and the signer
was the edge device, whose key signs ciphertext provenance in Phase 2, not the
querying user in Phase 4. A device credential was standing in for a user's
authorisation.

Both made this baseline's trapdoor **cheaper than the construction it
published**, which is the one thing a baseline may never be.

**What it does now.** `attribute_binding(SK_A)` is a SHA3-256 over the attribute
set *and its short preimages* `d_i`, mixed into the trapdoor digest, and the
signature uses `sk_U`. Binding to the attribute set alone would be forgeable —
which attributes a user holds is public, the preimages are not.

**The complexity claim survives — but only because the binding is cached.**
Table II costs the trapdoor at `O(n + T_PRF)` with no lattice sampling at query
time. `attribute_binding()` hashes the preimages, which are `O(m)` each — **792
KB at the configured `m = 33,792`, measured at 4.15 ms against a 1.4 ms
trapdoor.** Computing it per query would have reported this baseline as ~4×
slower than the construction it published, which is the same failure as
reporting it faster, pointed the other way.

It is derived once, at enrolment, and the query path mixes in 32 bytes:

| | cost |
|---|---|
| `attribute_binding()` uncached | 4.15 ms |
| cached | **0.0002 ms** |
| full `trapdoor()` | **1.386 ms** — matches the 1.4 ms measured before the fix |

`test_the_binding_is_not_recomputed_on_the_query_path` guards it. Enrolment's
lattice sampling is setup and untimed — **`abe.setup` TrapGen at `n = 768`
measures 4,710 s (78 min)**, once per experiment run.

**It also could not run at all until 2026-09-13.** `sample_discrete_gaussian`
applied its 14x rejection over-draw to the whole remaining output in ONE
allocation, so TrapGen's `(16896 x 16896)` R asked numpy for 3,996,647,424
int64 — 29.8 GiB of temporary to fill a 2.3 GiB result, an unconditional
`MemoryError` on the 15 GiB campaign host. Scheme 54's Exp. 1 and Exp. 4
exited 1 without measuring a point. The draw is now capped at 2^24 elements;
the sampled distribution is unchanged, and every other caller draws
`<= params.m` (33,792) so its RNG stream is bit-identical.

**Results affected.** Exp. 1 and Exp. 4 are the only experiments that call
`trapdoor()` on a measured path; both were **re-run on 2026-09-13** and the
`SUPERSEDED` markers removed. They are current and reportable. Exp. 2 and Exp. 3 call it in untimed setup only —
their numbers are unaffected and stay frozen.

## The measurement boundary

`abe_on_measured_path: false` is a recorded decision (2026-08-29), not an
omission:

- **Experiment 1** times trapdoor generation, which in this scheme is PRF
  tokenization plus a Dilithium3 signature — the paper's own headline claim
  (`O(n + T_PRF)`, "no lattice sampling at query time").
- **Experiment 2** times search over the fog-side hybrid index, which holds PRF
  tokens, not ciphertexts.
- **Experiment 3** is `d` independent Experiment 2 searches.

The lattice CP-ABE ciphertext `ct_abe` is therefore read by **none** of the
three; it is payload-key material. It is implemented in `abe.py` and exercised
by the tests, but it is on no measured path, and the flag records that so the
exclusion travels with every run rather than living only in prose.

**Session establishment is reported separately.** ML-KEM-768 encapsulation is
excluded from the Experiment 1 trapdoor curve because it happens once per
session, not once per query. Rather than exclude it silently, `main.py` measures
and prints it at startup.

## How it came into Experiment 4

Held out initially, pending two blockers. Both cleared on 2026-09-04:

1. `retrieve_verify` rebuilt the whole partition tree on every call — `O(N)`,
   not the `O(log N)` Table II claims — plus a linear leaf lookup. `finalize()`
   now retains the tree it already builds and `verify_record` proves against it:
   measured flat at 0.777 ms per call from `N = 500` to `N = 4000`, path length
   rising 9 → 12 (= log₂ N).
2. Experiment 4's boundary excludes fetch and decryption, but Algorithm 3 does
   verification **and** hybrid key reconstruction in one call.
   `scheme.verify_record` is its verification half alone and is what the runner
   times, so this scheme's number covers the same work as every other arm's.
   `retrieve_verify` still performs both halves and is untouched.

## Implementation notes

- **Single Trusted Authority.** Do not describe this scheme as multi-authority
  anywhere — the paper does not claim it, and an earlier mislabelling of another
  baseline's capabilities is exactly the error this repository avoids.
- Like the other baselines, this scheme fixes the **total** index size across
  the Experiment 3 `d` sweep while the proposed scheme fixes the **per-domain**
  size — opposite designs, so the curve shapes partly reflect the sizing rule
  rather than cross-domain orchestration alone.
